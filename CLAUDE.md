# ai-orchestrator-adt — Claude context

You are in the team-definition repo, not a target project. This repo defines the `/adt-*` slash commands, the behavioural defaults, and the sync/kanban engine. ADT is the orchestrator — it holds an AI development team to a gated path — and it is driven by typing `/adt-*` commands in Claude Code; there is no launcher daemon that polls or auto-spawns. Target projects (e.g., a second project) live in their own repos; a per-user config at `~/.adt/projects/<name>.yaml` (generated by `adt-install.sh`) points at them.

## What lives here vs in the target project

| Lives here (team repo) | Lives in target project |
|---|---|
| Command playbooks (`commands/`) | Backlog (`~/.adt/<project>/cache/`) |
| Backlog frontmatter schema (`schema/`) | Inbox (`.adt/inbox/`) |
| Behavioural defaults (`defaults/`) | The actual code, branches, PRs |
| Sync + kanban engine (`tools/`) | Per-project `CLAUDE.md` + the backlog (Issues + cache) |

## If you're the operator

You're driving a ticket end to end against a project config. The `/adt-*` command playbooks ARE the operating instructions, keyed by kanban lane; the behavioural discipline lives in `defaults/rules/` (working-style + the git workflow, loaded every session). The target project's `CLAUDE.md` ALSO applies and takes precedence on project-specific rules.

## If you're editing the team itself

You're improving the team. Most edits land in `commands/<cmd>.md` (refining a playbook — the commands are flat, one file per command) or `defaults/rules/` (refining the always-on behavioural discipline). A lesson worth keeping is written into the playbook or rule it changes — there is no separate lessons archive.

## Key rules

1. The team is portable — never hard-code project paths. Always read from the project config (`~/.adt/projects/<name>.yaml`, or `projects/<name>.yaml` for the shipped example).
2. After the merge gates pass, **offer the merge — the human chooses who merges** (themselves, or the agent on their say-so). Never merge silently; never merge with gates unmet. On a repo whose `main` is pinned by consumers as a submodule (ADT itself is one), use a merge commit, not squash — squashing orphans the SHA those consumers pin.
3. `/adt-block` exists for a reason — use it instead of guessing on PO-level decisions.
4. `/adt-decide` records anything you'd want to re-read in 6 months.
5. Commands, hooks, and `lib/` talk to GitHub via `gh api repos/…` (REST/core)
   — never the `gh pr`/`gh issue` view/create/merge porcelain, which bills the
   separate 5000-point GraphQL pool and exhausts it in one heavy PR session
   (ADT-109). GraphQL only where no REST API exists (Projects v2).
   Enforced in two places because the two layers need different instruments:
   the playbook layer is graded by `tests/test_gh_api_discipline.sh`; the python
   layer by `_BANNED_PORCELAIN` inside `tools/adt_sync.py`, checked in `_gh()`,
   which is formatting-independent and catches the indirect-argv form no
   line-oriented grep can follow (ADT-147).
6. Any command creating a GitHub Issue for a ticket in its own project must
   claim it on the create call — `gh issue create … --label "adt:filing"`.
   Without it, an `adt watch` tick between the Issue existing and its cache file
   existing reconstructs a duplicate stub, silently (ADT-116). A session filing
   into another project's repo must not claim: nothing on that side releases the
   label, so the ticket is missing from that board for an hour. See the
   git-workflow rule §D6. This
   is a playbook rule, carried by the playbooks themselves — ADT-280 removed
   the test that asserted their wording.

7. **Two enforced rules are graded, not asked for (ADT-114).** *Verify before
   asserting* — a claim about the system must trace to something run or read in
   that turn (`adt-phrase-linter.sh`). *No casual deferral* — filing a follow-on
   ticket needs all three of unforeseen, significant deviation required, and
   human approved, and there is **no autonomous path to filing**
   (`adt-deferral-guard.sh` denies `gh issue create`, or any gh api
   call that creates an Issue, without a `role: user` authorisation). Work discovered mid-build is fixed in the diff; see the
   deviation loop in `commands/build.md` and `docs/self-verification.md`.

## Testing

ADT is two things and they are tested differently.

**The product** — commands, playbooks, rules, agents. Markdown an agent reads and
acts on. There are no tests for this. A grep proving a playbook still contains a
sentence does not prove an agent reading it does the right thing, and it makes
the prose immovable. Validate the product by running it: file a ticket, drive it
through the lanes, watch it land. ADT-280 deleted the seven tests that asserted
playbook wording.

**The build** — `tools/*.py`, `lib/*.sh`, the hooks, the installer. Real code
with branches and races, and the half where a bug ships quietly. This is what the
suite covers.

A small third set checks that a documented surface matches the shipped one:
`tests/test_surface_catalogue.py` (`docs/references.md` lists the commands that
exist) and `tests/test_installed_copies_match_source.sh` (`.claude/` is what a
clean install writes).

**There is no CI.** The four GitHub Actions workflows were removed in ADT-280,
after they consumed ~2,500 of 3,000 monthly Actions minutes in seven days: the
`tests` workflow ran on a macOS runner, billed at ten times the Linux rate, on
every PR push regardless of what the diff touched. Nothing checks a PR
automatically now. ADR-036 settles that this is deliberate and not a gap waiting
to be filled: CI stays off while zurichrich is the only committer and runs the
suite locally. The revisit that was owed at publication happened, and ADR-036 is
its answer; the next revisit is a second committer. If it returns it is a
Linux runner, the pytest half only, triggered on paths that touch code — the
shell half cannot run on Linux without work.

**Which tests are owed: the diff decides.** Not the lane, not a resume, not "a PR
was opened" (working-style #7).

- Diff touches `commands/` or `defaults/rules/` — no suite. Drive a ticket.
- Diff touches `tools/adt_sync.py` — run the sync tests, not the shell half.
- Diff touches a hook — run that hook's test.
- Full suite — before a release, or when something structural moved.

The full suite, when it is genuinely owed:

```
python3 -m pytest tools/tests/ tests/ -q
bash tests/run-shell-suite.sh
```

The root `pytest.ini` sets only `norecursedirs` and deliberately does not set
`testpaths`, so the suite cannot be inferred from the repo layout. `find` inside
`run-shell-suite.sh` is what discovers the shell half; a hardcoded list would rot
the way CLAUDE.md's old list of eleven did.

The annotated list below is a reading aid — what each suite is *for* — and not
the set that runs. It is curated, not exhaustive: it names the suites worth
knowing about, while discovery covers every one of them. That is the point of
the split — the list can be incomplete without anything going unrun.
